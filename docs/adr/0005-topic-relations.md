# ADR 0005 — Topic relations (connect topics that touch but are not the same issue)

Status: accepted — 2026-06-10
Supersedes/amends: extends ADR 0003 (persistent topics by subject threading)

## Context

ADR 0003 gave us threading: one persistent **Topic** carries many **Decisions** when they are
the same real-world issue. The comprehensive link pass (Milestone 6) — an exhaustive review of
all 285 topics — showed that "same issue" is only one of several real connections residents care
about. Topics also relate without being the same thing:

- An umbrella **report** (e.g. *Local Transport Forum recommendations*) or a **masterplan**
  (e.g. *Dulwich Hill Village Masterplan*) sits ABOVE the individual works it adopts/contains.
- Several **motions** about one precinct attack it from different angles (e.g. St Peters
  parklands *compensation* vs *contamination* vs *WestConnex remediation*) — distinct asks,
  same place.
- A new scheme **replaces** an earlier one at the same location.

Merging these would erase distinct council decisions (a published falsehood, the same risk ADR
0003 guards against for threading). But leaving them disconnected hides the context a resident
needs ("what else is happening here?").

## Decision

Add a `topic_relations` table (migration 0004) holding non-merge connections between two topics:

| kind | meaning | direction |
|---|---|---|
| `parent-child` | topic_a contains/adopts topic_b | a = parent, b = child |
| `supersedes` | topic_a replaces topic_b | a = newer, b = older |
| `related` | same place/theme, no hierarchy | symmetric, store a<b by id |

- **`merge` is not a relation kind.** Confirmed same-issue links stay in the threading model:
  repoint decisions, drop the orphan topic, write a `source='human'` subject alias (as in
  migration 0003). `topic_relations` only holds connections that must NOT collapse into one topic.
- `source='human'` for review-pass confirmations; `source='auto'` reserved for a future matcher
  that proposes relations. A wrong relation is far cheaper than a wrong merge (it adds context,
  it doesn't rewrite history), but human-confirmed relations still form the trusted base.
- Relations are how future ingest will offer "see also" context and how the frontend will show a
  topic's neighbourhood. Ingest teaching: confirmed relations + the subject-alias base from
  threading together give the pipeline a model of how this council's issues connect.

## Consequences

- New table, two indexes; no change to existing topic/decision/alias semantics.
- The frontend (Milestone 7) can render a topic's parents/children/related/superseded links.
- Candidate relations are generated by clustering topics on shared *local* streets (arterials
  excluded — they bridge unrelated items) and argued to a recommendation against the infocouncil
  source documents before any row is written.
